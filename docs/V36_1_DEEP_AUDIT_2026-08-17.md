# Kosif v36.1 — Deep Audit Report

Date: 2026-08-17

## Scope

This review covered the current Kosif v36 production architecture, repository history, prior project decisions, the historical archive `تمحيص-v35-مع-مكتبة-المعايير.zip`, the standards-library package, AI/Review Council flows, PWA behavior, Cloudflare Worker routing, and iPhone-sized runtime behavior.

The uploaded v35 archive was treated as a **historical capability reference**, not as an authoritative replacement for current standards data. Its reader contained capabilities that had been lost later, but its standards extraction also contained known OCR/classification inconsistencies. The release therefore restores capabilities while keeping the corrected current data.

## Critical defects found and fixed

### 1. False AI Active state

The old UI equated `key exists` with `AI Active`. This is incorrect and was visible on iPhone even while the server returned `AI_LOCKED`.

v36.1 replaces this with four states:
- AI locked.
- owner session open but no key.
- key entered but not tested.
- connected only after a real provider test succeeds.

`KosifAIClient.hasKey()` no longer means mere key presence; it now follows verified-connection semantics.

### 2. API key field was writable before owner authorization

All supported key fields are now cleared and `readonly` while the owner session is locked. Pointer/focus opens the owner-password gate, and `beforeinput`/paste are blocked. This applies to the main AI settings and Gemini/OpenAI/Claude Review Council keys.

### 3. Server-side AI use could not rely on UI state

A server-enforced tested-key gate was added. `/api/kosif/ai/test` performs a real short request using the selected provider/model/key. Only a successful response records a SHA-256 fingerprint of `provider + model + key` inside the current 8-hour owner session. Production AI calls require an exact fingerprint match. Changing provider, model, or key invalidates approval.

No raw provider API key is persisted by this gate.

### 4. Review Council provider verification

Each Council member now has its own connection test. At least two tested providers are required before a Council run. Claude may act as chair/adjudicator only when the Claude key/model itself passed testing.

### 5. Standards reader feature regression

The v35 archive proved that the standards reader previously had richer reading capabilities. v36.1 restores:
- Arabic TTS.
- speech highlighting.
- Media Session controls.
- Wake Lock.
- auto-scroll speeds 1–10.
- first-touch auto-scroll stop.
- sleep timer.
- jump by `IAS 16`, `IFRS 9`, `IFRIC`, or `SIC` code.
- chapter export.
- reader journal export.
- reading streak.

These features run on the current corrected standards data rather than reverting the older archive.

### 6. 2025 standards metadata count

`public/standards/data/library.json` said the 2025 book contained 33 chapters while 34 packaged chapter files exist. Chapter 34 was inspected and is a real chapter titled `معيار محاسبة الزكاة (المعدل)`. Metadata was corrected to 34 and the permanent Deep Audit now fails if metadata counts diverge from packaged chapters again.

### 7. PWA cache generation

The main application cache was bumped to `kosif-native-v36-1-app` and the standards cache to `kosif-native-v36-1-standards`. API responses remain excluded from Service Worker caching.

## Standards/source policy

Saudi application keeps SOCPA-adopted standards as the primary local authority. International IFRS/IAASB sources remain update/reference sources unless local adoption/effective status has been verified. IFRS 18 and IFRS 19 remain period-aware readiness items rather than silently becoming current requirements before their effective period or a valid early-adoption decision.

Official reference families used by the project include:
- SOCPA professional/accounting/auditing standards pages.
- IFRS Foundation issued standards pages.
- IAASB handbook/standards sources.
- official provider documentation for OpenAI and Google Gemini model defaults.

## Release rule going forward

A higher version number is not evidence that every capability is present. Future releases should preserve this audit matrix and use historical builds only to recover demonstrated capabilities, while current corrected data and verified official-source policy remain authoritative for the application state.
